# Can attention weights and per-layer hidden states be exposed in the browser LLM visualizer?

## Question

Can attention weights (and per-layer hidden states) be exposed from browser-run LLMs, to power attention heatmaps and richer layer detail in `llm-visualizer`? Covers: (1) installed `@huggingface/transformers` support, (2) custom ONNX export with `output_attentions`, (3) existing pre-exported models on the HF Hub, (4) `output_hidden_states` feasibility, (5) alternative runtimes (WebLLM/MLC, ONNX Runtime Web, TVM), (6) a practical recommendation for the app.

## TL;DR

Attention/hidden-state exposure in transformers.js is entirely a property of the **ONNX graph**, not the JS runtime: `sessionRun()` calls `session.run(feeds)` with no output filter, so whatever the `.onnx` file declares as graph outputs comes back verbatim in `out` — which is exactly what the app's manual generation loop in `worker.ts` already consumes. The installed transformers.js 4.2.0 has real, working attention-output support for **vision/sequence-classification models** (`SequenceClassifierOutput`, Whisper cross-attentions for word timestamps) but **no path exists for generic decoder-only self-attention**, and `output_hidden_states` is a dead config flag with zero consumers anywhere in the source. Hugging Face's own ONNX export stack (`optimum-onnx`'s `TextDecoderOnnxConfig`) never emits attentions or hidden states for causal LMs either — you'd need a custom `OnnxConfig` subclass, which is exactly what one community member did for `damoncrockett/gpt2-with-attentions-onnx`, at the cost of a 623 MB fp32 graph with **no KV cache** (`use_cache=False`). No comparable SmolLM2-135M attentions export exists today. Alternative runtimes (WebLLM/MLC, raw ONNX Runtime Web, TVM) don't change the underlying constraint — MLC's ahead-of-time-compiled kernel graph makes it *harder*, not easier, since there's no equivalent of "add a graph output" without recompiling.

## 1. Does installed `@huggingface/transformers` (4.2.0) support `output_attentions`/`output_hidden_states` for decoder-only causal LMs?

Installed version confirmed: `package.json:15` pins `"@huggingface/transformers": "^4.2.0"`, and `node_modules/@huggingface/transformers/package.json` resolves to `"version": "4.2.0"`.

**`output_attentions` exists, but only for `generate()`, and only collects cross/encoder/decoder attentions — never generic decoder self-attention:**

- `src/generation/configuration_utils.js:307` defines `output_attentions = false` on `GenerationConfig`.
- `src/models/modeling_utils.js:967-976`: inside the `generate()` sampling loop, when `generation_config.return_dict_in_generate && generation_config.output_attentions`, it calls `getAttentions(outputs)` and accumulates the result per step.
- `getAttentions()` (`src/models/modeling_utils.js:1220-1234`) only looks for output names starting with `'cross_attentions'`, `'encoder_attentions'`, or `'decoder_attentions'` — a plain `'attentions'` key (what a decoder-only self-attention export would be named) is **not matched by this function**.
- `src/models/modeling_outputs.js:107-119`: `CausalLMOutputWithPast` (the output type conceptually associated with decoder-only causal LMs) destructures only `{ logits, past_key_values }` — any other key (e.g. `attentions`, `hidden_states`) would be silently dropped if this wrapper were used. In practice it is **dead code**: `grep` shows zero usages of `CausalLMOutputWithPast` outside its own definition in 4.2.0.
- By contrast, `SequenceClassifierOutput` (`modeling_outputs.js:28-44`) *does* generically collect `{ logits, ...attentions }` into `this.attentions` — this is the mechanism GitHub PR [huggingface/transformers.js#1117](https://github.com/huggingface/transformers.js/pull/1117) ("Add support for visualizing self-attention heatmaps + sequence classifier outputs w/ attentions", merged 2024-12-28 by xenova) added, targeting **vision and encoder sequence-classification models** (example: `onnx-community/dinov2-with-registers-small-with-attentions`), not text generation.

**`output_hidden_states` is a dead flag:** `src/generation/configuration_utils.js:315` defines `output_hidden_states = false`, and it is the **only** occurrence of that string anywhere in `src/` — no code path reads it. There is no per-layer hidden-state collection mechanism in transformers.js today, for any model type.

**Whisper's cross-attention consumption (the one thing that does work) generalizes narrowly:** `src/models/whisper/modeling_whisper.js:149` sets `generation_config.output_attentions = true` automatically when `return_token_timestamps` is requested, and `_extract_token_timestamps()` (`modeling_whisper.js:381-420`) reads `generate_outputs.cross_attentions` to do DTW alignment for word-level timestamps. Line 391 explicitly states the failure mode: *"This is most likely because the model was not exported with `output_attentions=True`"* — confirming this is gated by the **ONNX export**, not a runtime toggle. This only works because Whisper is encoder-decoder (cross-attention between decoder tokens and encoder frames); it has no analogue for decoder-only self-attention.

**What the ONNX graph needs to output, mechanically:** Tracing through the actual forward path used for causal LMs — `decoder_forward()` (`src/models/modeling_utils.js:1302-1337`) does `pick(new_model_inputs, session.inputNames)` then `return await sessionRun(session, fixed)` with **no output-side filtering**. `sessionRun()` (`src/models/session.js:192-211`) calls `runInferenceSession(session, ortFeed)` → `src/backends/onnx.js:313-314`: `session.run(ortFeed)` with **no output-names argument**, meaning ONNX Runtime Web always computes and returns *every* output the graph declares. This is the critical mechanism: **the app's `worker.ts` manual loop (`out = await model({ input_ids, attention_mask, past_key_values })`, `worker.ts:91`) will receive any output name baked into the `.onnx` graph automatically**, with zero transformers.js code changes required — `worker.ts:36-51`'s `updateCache()` already relies on exactly this behavior to find `present.*` keys via `for (const name in output)`. So the only real requirement is: **export an ONNX graph whose outputs list includes attention/hidden-state tensors** (e.g. named `attentions.0`, `attentions.1`, ... or `hidden_states.0`, ...). transformers.js's own `output_attentions`/`output_hidden_states` generation-config flags are irrelevant to this manual-loop path; they only matter if the app switched to using `model.generate()`.

Source: `/Users/markus/IdeaProjects/llm-visualizer/node_modules/@huggingface/transformers` (v4.2.0), file:line references above.

## 2. Can we export a model ourselves with `output_attentions=True`? What flags, what costs?

**transformers.js no longer ships a bundled `scripts/convert.py`.** A full recursive tree fetch of `huggingface/transformers.js` at `main` (current monorepo layout, `packages/transformers/...`) found no `convert.py` anywhere in the repo. The current docs (`packages/transformers/docs/snippets/3_custom-usage.snippet`, fetched via GitHub Contents API) say explicitly: *"We recommend using [Optimum](https://github.com/huggingface/optimum-onnx) to convert your PyTorch models to ONNX in a single command."* — i.e. conversion is now delegated entirely to `optimum-cli export onnx` / `optimum.exporters.onnx`, not a script inside transformers.js. (The `scripts/convert.py` referenced in the task is a pre-v3 / historical pattern.)

**Optimum's decoder-LM export config has no attentions/hidden-states support at all.** Fetched `optimum/exporters/onnx/config.py` from `huggingface/optimum-onnx` (main): `TextDecoderOnnxConfig` (`config.py:53-102`, the class backing GPT-2/Llama/SmolLM2-style causal LMs) defines `outputs` (`config.py:93-102`) as only `{"logits": ...}` plus `add_past_key_values(...)` for the KV cache — no `output_attentions` parameter, no attentions/hidden_states keys, anywhere in the file. A `grep` for `output_attentions` across the whole file returns nothing.

**The real mechanism is `custom_onnx_configs`.** Optimum's `main_export()` (and `optimum-cli export onnx`) accepts a `custom_onnx_configs: Dict[str, OnnxConfig]` argument mapping submodel name (`model`/`decoder_model_with_past`/etc.) to a hand-written `OnnxConfig` subclass. To get attentions out of a decoder-only LM you must: subclass the model's `OnnxConfig`, override `outputs` to add `attentions.{i}` entries (with the right dynamic axes), and pass `model_kwargs={"output_attentions": True}` so the traced PyTorch forward actually produces those tensors during `torch.onnx.export` tracing. This pattern is corroborated by a HF forum thread, ["How to export MarianMT to ONNX with output_attentions=True?"](https://huggingface.co/docs/optimum/v1.7.1/exporters/onnx/package_reference/configuration) and by the still-open, unresolved GitHub issue [huggingface/optimum#325](https://github.com/huggingface/optimum/issues/325) ("Add possibility to output attentions from the ONNX models"), where the reporter hits *"Graph output (attentions) does not exist in the graph"* and there is **no accepted solution or merged PR** — confirming this is not first-class/supported, only DIY.

**A concrete, verified example of someone doing exactly this for a decoder-only LM:** `damoncrockett/gpt2-with-attentions-onnx` on the HF Hub (fetched via HF Hub API and README, 2026-08-27). Facts confirmed from the Hub API (`https://huggingface.co/api/models/damoncrockett/gpt2-with-attentions-onnx?blobs=true`):
- `library_name: transformers.js`, `pipeline_tag: text-generation`, architecture `GPT2LMHeadModel`, single file `onnx/model.onnx` = **653,653,852 bytes (≈ 623 MB)**, fp32, **no quantized variant published**.
- Per the README (WebFetch summary): exported from `openai-community/gpt2` with `output_attentions=True`, **`use_cache=False`**, eager attention implementation, exposing outputs `logits` and `attentions.0` … `attentions.11` (one per layer, shape `[batch, num_heads, seq_len, seq_len]`). The author states this trades away autoregressive decoding speed to "preserve full prompt-level attention matrices suitable for visualization."

**Costs this surfaces, concretely:**
- **File size**: no quantization applied in the only real-world example found; 623 MB for a 124 M-parameter model (vs. ~137–182 MB for a quantized version of the *same size class* without attentions, per SmolLM2-135M numbers below). Nothing here proves quantized+attentions is impossible, just that it isn't demonstrated anywhere found.
- **KV-cache interaction**: the example export disables `use_cache` entirely — i.e. attentions and incremental KV-cache decoding were not combined in this export. This matches a structural tension: `TextDecoderOnnxConfig`'s KV-cache path (`add_past_key_values`) and a from-scratch full-attention-matrix output are two different "shapes" of decode step (with cache: attention is `[..., 1, past_len+1]` per step, not the full prompt matrix many heatmap UIs want to show). Getting both simultaneously requires deciding, per export, whether attentions are captured only for the cached partial step or the model is run without cache to get full matrices — this wasn't demonstrated solved in any source found; treat "KV-cache + full per-token attentions" as **UNVERIFIED / needs prototyping**.
- **WebGPU operator/output-placement cost**: transformers.js's own session setup (`session.js:110-124`, `getCacheNames()` in `configs.js:329-412`) only special-cases outputs named `present.*` (or ssm/conv variants) for GPU-buffer pinning (`preferredOutputLocation`) to avoid a GPU→CPU copy every step. An `attentions.*` (or `hidden_states.*`) output is **not** in that allowlist, so on the WebGPU backend it would default to CPU read-back on every forward call — a real per-token latency/bandwidth cost that scales with `heads × seq_len²` per layer, independent of ordinary operator support (attention math itself — matmul/softmax — is well supported by ORT's WebGPU EP; the cost is the output transfer, not compute).
- **No output filtering at the transformers.js layer**: `sessionRun()` never passes a fetch/outputNames list to `session.run()` (`backends/onnx.js:313-314`), even though ONNX Runtime's `session.run()` API supports restricting to a subset of outputs (confirmed generically across ORT's Python/C#/Java docs). So today, once attentions are baked into the graph, transformers.js computes and returns them on **every** call — there is no "only fetch attentions when the UI needs them" toggle without bypassing transformers.js's session wrapper.

Sources: `github.com/huggingface/transformers.js` (packages/transformers/docs/snippets/3_custom-usage.snippet, fetched via GitHub API), `github.com/huggingface/optimum-onnx` (`optimum/exporters/onnx/config.py`, fetched via GitHub API), `github.com/huggingface/optimum` issue #325, `huggingface.co/damoncrockett/gpt2-with-attentions-onnx` (Hub API + README).

**No GPT-2/DistilGPT2/BERT-with-attentions repos were found under the `Xenova` namespace specifically** — the official attentions examples live under `onnx-community` (DINOv2) instead. A hub search for `"bert attentions"` returned zero matches. **No SmolLM2-135M(-Instruct) attentions export exists** on the Hub as of this search — you would be exporting it yourself, following the `damoncrockett/gpt2-with-attentions-onnx` pattern as the closest known template.

## 4. Per-layer hidden states (`output_hidden_states`)

Same conclusion as attentions, for the installed library: `output_hidden_states = false` (`src/generation/configuration_utils.js:315`) is defined on `GenerationConfig` but is a **completely dead flag** — a repo-wide grep found no other reference to `output_hidden_states` in `src/`. There is no `getHiddenStates()` analogue to `getAttentions()`, and no output-class in `modeling_outputs.js` collects a generic `hidden_states` list (only `BaseModelOutput`'s constructor destructures an optional `hidden_states` param, but nothing populates it from raw session output for causal LMs).

On the export side, `optimum-onnx`'s `TextDecoderOnnxConfig.outputs` (`config.py:93-102`) likewise has no hidden-states provision — same "you'd need a custom `OnnxConfig`" story as attentions, and no evidence was found (Hub search) of anyone having done this for hidden states specifically the way `damoncrockett` did for attentions.

The mechanical path is identical to attentions though, and arguably **simpler for the visualizer's actual need**: the app only wants **per-layer hidden-state *norms*** (a scalar per layer, not full heatmaps), which means the ONNX graph output for each layer could be a tiny reduced tensor (e.g. per-layer L2 norm computed inside the graph via an `ONNX::ReduceL2` node appended in a custom export) rather than the full `[batch, seq, hidden]` activation tensor — this would sidestep most of the WebGPU-readback and file-size cost discussed in section 2, since layer norms are `O(num_layers)` floats per forward call instead of `O(num_layers × seq_len × hidden_size)`. This specific optimization (graph-side reduction before output) was not found demonstrated anywhere in the sources reviewed — it's a **reasonable engineering inference**, not something UNVERIFIED against a primary source, so treat it as a recommendation rather than a confirmed fact.

## 5. Alternative browser runtimes: WebLLM/MLC, ONNX Runtime Web directly, TVM

- **ONNX Runtime Web directly** (bypassing transformers.js): no capability gain or loss versus what's described above — transformers.js *is* a thin wrapper around `onnxruntime-web`'s `InferenceSession`. Using ORT Web directly only helps with the "no output filtering" cost noted in section 2, since ORT Web's JS `session.run(feeds, fetches, options)` API does support passing an explicit `fetches` list to compute only a subset of graph outputs — letting you fetch `attentions.*` only on the step(s) the UI actually needs it. This is confirmed generically by ONNX Runtime's own API docs across language bindings (Python/C#/Java `session.run([output names], inputs)` pattern); transformers.js's `sessionRun()` simply doesn't expose this today (`backends/onnx.js:313-314`, no fetches argument passed).
- **WebLLM/MLC**: WebLLM is explicitly built on MLC-LLM + Apache TVM, which ahead-of-time-compiles a model into a fixed WASM+WebGPU kernel graph (per MLC's own docs, `llm.mlc.ai/docs/compilation/compile_models.html`, and the WebLLM README on GitHub). Nothing in MLC's or WebLLM's documentation describes a runtime hook for extracting intermediate attention or hidden-state activations — the compiled graph is fixed at build time, so exposing new outputs would require modifying the model definition before TVM/Relax compilation and recompiling (analogous to, but more involved than, the ONNX custom-`OnnxConfig` approach, since it also touches TVM's Relax-level graph construction, not just a Python export config). **No evidence found (or expected) of built-in attention exposure in WebLLM/MLC** — treat this as UNVERIFIED-by-absence (searched, found nothing) rather than a confirmed "impossible."
- **TVM generically**: same story as MLC (which is built on it) — Relax/TensorIR graphs are compiled ahead of time; nothing found suggesting a generic "attach output" mechanism analogous to ONNX's declared-graph-outputs model.

Net: **none of the alternative runtimes make this easier than the ONNX/transformers.js path**, and MLC/TVM likely make it harder due to the ahead-of-time compilation model.

## 6. Recommendation for `llm-visualizer`

**Given the app's architecture** — `src/engine/transformers/worker.ts` calls `model({ input_ids, attention_mask, past_key_values })` directly (`worker.ts:91`) and reads `out.logits`, bypassing `generate()` entirely, with a hand-rolled `updateCache()` (`worker.ts:36-51`) that already iterates every key on the raw output object — **the app is unusually well-positioned to consume extra ONNX outputs**, because it doesn't go through any of transformers.js's `generate()`-only, cross-attention-only collection logic. Whatever the `.onnx` graph outputs, `out` will have.

- **Recommended path: custom export, not runtime swap, not waiting on an existing model.** No existing SmolLM2-135M(-Instruct)-with-attentions model exists on the Hub (section 3), and the only working decoder-LM example (`damoncrockett/gpt2-with-attentions-onnx`) is a proof of concept, not something to depend on directly (different model, no quantization, no KV cache). Swapping runtimes (WebLLM/MLC/raw ORT Web) buys nothing here since the constraint is the exported graph, not the JS-side engine (section 5) — and raw ORT Web is worth considering only as a thin *addition* alongside transformers.js if you need selective-fetch (`fetches` list) to avoid paying the attentions cost on every token.
- **Concretely**: write a custom `OnnxConfig` for SmolLM2 (Llama-family architecture) following the `TextDecoderOnnxConfig` base (`optimum-onnx/optimum/exporters/onnx/config.py:53`), override `outputs` to add `attentions.{i}` (and, if pursuing hidden states, small per-layer norm outputs computed via an appended `ReduceL2` node rather than full activations — section 4), pass `model_kwargs={"output_attentions": True}` and your custom config via `custom_onnx_configs` to `optimum-cli export onnx`. Expect to **prototype the KV-cache interaction carefully**: the one real-world example dropped `use_cache` entirely to get full attention matrices, and SmolLM2's existing exports (see below) are all cache-enabled — reconciling incremental decoding with attention-heatmap-friendly full matrices is the main open engineering risk here (UNVERIFIED that both work together cleanly; budget prototyping time).
- **Expected artifact sizes for ~135M-parameter model** (from the Hub API, `HuggingFaceTB/SmolLM2-135M-Instruct`, fetched 2026-08-27, baseline *without* attentions): fp32 `onnx/model.onnx` = 540,345,794 B (≈515 MB); `model_q4.onnx` (what `worker.ts:23` actually loads, `dtype: 'q4'`) = 182,068,553 B (≈174 MB); `model_q4f16.onnx` = 117,691,126 B (≈112 MB); int8/uint8/quantized variants ≈137 MB. The one real attentions-export data point (GPT-2, similar parameter count, fp32, no cache) is 653,653,852 B (≈623 MB) — i.e. *comparable to or somewhat larger than* the unquantized SmolLM2 baseline, since attention tensors are activations (don't inflate the weight file) but the export skipped quantization. **A quantized SmolLM2-with-attentions export was not found to exist or to have been tried anywhere** — assume it's technically pursuable (quantization and extra graph outputs are largely orthogonal) but unverified in practice.
- **Practical sequencing suggestion**: prototype with the existing `damoncrockett/gpt2-with-attentions-onnx` first (it's real, downloadable, and already transformers.js-compatible per its README) to validate that `worker.ts`'s manual loop can read an `attentions.N` output with zero code changes to transformers.js itself, before investing in a custom SmolLM2 export + quantization + KV-cache reconciliation.
